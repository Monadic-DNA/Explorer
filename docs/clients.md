# Web, Android, and iOS clients

Explorer has three separate UIs backed by one Rust library:

- `app/`: Next.js/React web UI and the existing HTTP backend.
- `apps/android/`: Kotlin, Jetpack Compose, Android 8+ (API 26).
- `apps/ios/`: SwiftUI, iOS 17+; Xcode project generated using XcodeGen.
- `crates/explorer-core/`: portable client domain logic.

The mobile apps use native navigation, lists, forms, file pickers, and secure storage. They do not embed the web UI. The apps have no sign-in. Mobile purchases use StoreKit 2 / Play Billing, and stablecoin payments are available only on Web.

## Shared core and platform boundaries

Rust implements genotype format detection/parsing, bounded gzip decoding, variant matching, OR/beta scoring, quality/evidence interpretation, result serialization, preview selection, report selection and prompts, personalization parsing, provider configuration, promo verification, native access policy, the native encrypted store and its sync, and native nilAI authentication tokens. The report regression fixtures preserve the prior web report selection and prompt behavior.

Normal operations on all hosts use the same versioned JSON protocol: `{version:1, operation, input}` returns `{ok:true,value}` or `{ok:false,error}`. `crates/explorer-core/src/lib.rs` lists operations. Recoverable input errors do not panic. Large native DNA imports use a UniFFI byte-buffer entry point to avoid base64/JSON copies; this calls the same bounded decoder, parser and hash function. On native, an encrypted SQLite store owned by the core holds genotypes, results and customization; hosts page through results instead of copying them. Closing the store invalidates its handle. The web keeps in-memory Rust sessions.

The web adapter (`lib/core.ts`) loads an import-free WASM module synchronously, including in workers and server rendering. Existing TypeScript functions retain their public signatures and delegate domain work to Rust. Kotlin and Swift call the same entry point through generated UniFFI bindings, using a native shared/static library respectively. Generated bindings, WASM source, native libraries, and Xcode projects are ignored and regenerated from the locked Rust workspace.

HTTP transport, provider SDK integration, cancellation, UI state, browser IndexedDB, platform file access, and OS credential storage remain in their hosts. The backend's PostgreSQL/pgvector search, authentication verification, Stripe, and blockchain services remain server-side. The web app retains its IndexedDB catalog cache and WebCrypto nonextractable device key; mobile Run All matches the catalog snapshot bundled with each app release, on device and offline. Native catalog browsing and search require a network connection.

## Features

Both native apps provide DNA import, exact/semantic search and trait filtering, study details and publication links, individual matching, Run All, saved-result filtering and TSV import/export, chat, Health/Healthspan/Top traits/Overview reports, optional personalization, provider settings, an encrypted on-device store with end-to-end encrypted sync, native store purchases, restore and subscription management. Chat and paid reports check the store entitlements on the device. Stablecoin payments are available only on Web.

The layout and platform interactions differ from the web app. Mobile report output supports export as Markdown; Android displays the report text directly. Web-specific advertising, attribution, social-account linking, and browser catalog caching are not duplicated as native screens. Mobile provides no external payment links; Web retains Stripe and wallet checkout. Both native report screens expose follow-up questions generated by the shared core.

## Web development

Install Node 24, rustup, and the PostgreSQL/pgvector backend described in the main README. Then:

```sh
npm ci
npm run dev                 # builds WASM first
npm test                    # actual JS/WASM adapter regression tests
npm run core:test           # native Rust contract tests
npm run lint
npx tsc --noEmit
npm run build
```

Keep `POSTGRES_DB` pointed at your environment's local database during development. No database credentials or server provider keys are embedded in mobile apps. CI production builds do not require database access during compilation.

## Bundled research catalog

Each native release bundles the research catalog snapshot pinned in `catalog/snapshot.json`; Run All reads it on device instead of paging the API. The snapshot is about 20 MB (zstd), stores study-level text once per study, and records its version, row count and SHA-256.

To update it for a release:

```sh
node scripts/catalog-snapshot.mjs      # prompts for the Postgres connection string; read-only export
s3cmd put --acl-public catalog/dist/<file>.zst s3://monadic-dna-explorer/<file>.zst
git add catalog/snapshot.json          # catalog/dist/ is not committed
```

`CATALOG_DATABASE_URL` can supply the connection string non-interactively. The script verifies the server certificate like `lib/db.ts` (`certs/ca-certificate.crt` or `DATABASE_CA_CERT`). `scripts/build-native.mjs` places the pinned snapshot in each app: it uses `catalog/dist/` or its download cache under `target/catalog/` when the SHA-256 matches, otherwise downloads it from the Space's CDN endpoint, and fails on a mismatch. Android builds stop early if the snapshot has not been placed.

## Android

Requirements: JDK 21, Android SDK platform 35/build tools 35.0.0, NDK 27.2.12479018, Node 24, rustup. Set `ANDROID_HOME` to the SDK location. The checked-in Gradle wrapper pins Gradle 8.11.1 and verifies its SHA-256 checksum.

```sh
node scripts/build-native.mjs android arm64-v8a
cd apps/android
./gradlew assembleDebug testDebugUnitTest lintDebug
# Output: app/build/outputs/apk/debug/app-debug.apk
```

Host JVM tests load the real Rust library built by the script. For an x86 emulator, first build the matching Rust ABI and select it for packaging:

```sh
node scripts/build-native.mjs android x86_64
cd apps/android
./gradlew -PexplorerAbis=x86_64 assembleDebug connectedDebugAndroidTest
```

`-PexplorerAbis=arm64-v8a,x86_64` packages both, after generating both libraries. Release builds require your signing configuration. Debug builds permit `http://10.0.2.2:3000`, `localhost`, and `127.0.0.1` for the local backend; release catalog/account traffic requires HTTPS. User-configured Ollama traffic may use HTTP. Change the backend origin in Settings. An emulator's localhost is the emulator itself.

## iOS

Requires macOS, Xcode with iOS 17+ SDK/simulators, Node 24, rustup, and XcodeGen (`brew install xcodegen`).

```sh
node scripts/build-native.mjs ios simulator
xcodebuild -project apps/ios/Explorer.xcodeproj -scheme Explorer \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  -derivedDataPath apps/ios/build test CODE_SIGNING_ALLOWED=NO
# Substitute an installed simulator from: xcrun simctl list devices available
```

For a device: `node scripts/build-native.mjs ios device`, open the generated project, set your development team and signing, and run. Rust libraries are linked by platform and architecture. Generate both simulator architectures if building a universal simulator destination. `CARGO_TARGET_DIR` overrides are supported by Android and WASM generation; iOS project linkage expects the default repository `target/` directory.

The macOS CI job builds Rust, generates the project, selects an available iPhone simulator, and runs XCTest. iOS compilation and simulator tests run on macOS rather than this Linux workspace. The app build and all five XCTest tests passed in [CI run 39608592827](https://github.com/Monadic-DNA/Explorer/actions/runs/39608592827).

## Privacy, interoperability, and deployment

Native genotype data, saved study results and customization persist in an encrypted SQLite (SQLCipher) store owned by the Rust core. A random local key opens it; iOS wraps that key with a user-presence-protected Secure Enclave key and Android with an authenticated Keystore key, preferring StrongBox. Local keys are non-exportable and never sync. Store files are excluded from platform backups. Lock closes the store and clears visible results, chat and report state.

Sync is same-platform for now. It is on by default on iOS; Android offers it once on Home after the first import and asks for Google Drive access only if the user accepts. With sync on, a new iPhone or Android phone fills in automatically. Records are encrypted on device and stored in the user's own iCloud (CloudKit private database) or Google Drive app-data folder; the Monadic DNA backend stores no user data. The sync key travels through iCloud Keychain or Block Store, both end-to-end encrypted. Provider credentials are not synced.

See [native data store and sync](native-data-store.md) for the schema, key handling, record format, conflict rules and tests.


LLM use requires explicit result-sharing consent. Prompts go directly to the selected provider. HuggingFace needs a user-supplied key; Ollama uses the configured host; nilAI accepts a device key or the backend's one-use delegation flow. Native nilAI tokens are verified in regression tests using the existing Nillion SDK. Backend delegation retains its five-requests-per-minute limit; large Overview reports may require retrying or a user-provided nilAI key. Phone access to local Ollama requires reachable networking and appropriate platform transport configuration; production HTTPS endpoints are preferable.

## Mobile payments

Monadic DNA keeps no customer or purchase records. Stripe holds web customers, with the Dynamic wallet address as metadata; the App Store and Google Play hold mobile purchases. Mobile and web purchases are separate.

- Premium on mobile is an active subscription read on the device: `Transaction.currentEntitlements` (StoreKit 2) or Play's purchase list. The apps acknowledge Play purchases themselves.
- A report pass is a consumable store product. On Android it stays owned in Play until the report is generated, then the app consumes it. On iOS each verified transaction is credited once in the encrypted store and then finished; a report records a use. Credits and uses sync as the `report-passes` record and merge as sets, so a pass is never lost or spent twice. Purchases that arrive while data is locked stay unfinished and are credited after unlock.
- Product IDs are in `shared/billing-catalog.json`, which the core exposes as `billing_catalog`. Create the same IDs in App Store Connect and the Play Console. Stablecoin payments are available only on Web.

See [Run All performance and benchmarks](run-all-performance.md) for bounded native/browser parallelism, concurrent page loading, result parity and reproduction commands.
